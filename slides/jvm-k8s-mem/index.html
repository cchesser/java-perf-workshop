The trap

Heap tuning is not container tuning

  • The heap is only one part of JVM memory.
  • Kubernetes limits apply to the whole OS process.
  • Native memory can quietly eat the headroom.

The symptom

More memory, same surprise

OOMKilled

The container crosses its memory limit, even when heap graphs look calm.

$$$

Teams raise requests and limits "just to be safe", then pay for unused capacity.

Kubernetes controls

Requests schedule, limits enforce


resources:
  requests:
    memory: "768Mi"  # scheduler reserves this much node capacity
    cpu: "500m"
  limits:
    memory: "1Gi"    # cgroup hard boundary for the process
    cpu: "1"

Requests ask Kubernetes to place the pod where at least that much capacity is available. Limits are the hard cgroup boundary the process must stay under.

Java 17+

The JVM now sees more of the container

  • Java 17 includes cgroups v2 support and container-aware OS metrics.
  • Heap ergonomics can size from the container limit, not the node.
  • JDK 23 and newer 17/21 updates expose better cgroup memory details in diagnostics.

First check

Prove the JVM sees your limit


java -XshowSettings:system -version
jcmd <pid> VM.info
java -Xlog:os+container=debug -version

Use the first two for normal checks; use logging when the JVM's view looks wrong.

Example

-XshowSettings:system surfaces cgroups


$ java -XshowSettings:system -version
Operating System Metrics:
    Provider: cgroupv2
    Effective CPU Count: 1
    CPU Quota: 100000us
    CPU Period: 100000us
    Memory Limit: 1.00G
    Memory & Swap Limit: 1.00G
  • Provider: cgroupv2 means the JVM is reading Linux's unified cgroup hierarchy, available since Linux 4.5 in 2016.
  • Memory Limit: 1.00G is the ceiling for heap plus native memory.
  • Effective CPU Count: 1 influences GC threads, JIT threads, and application parallelism.
  • CPU Quota and CPU Period should line up with the deployment CPU limit.

This is the quick "am I sizing from the pod or the node?" check.

Example

Set MaxRAMPercentage in the pod spec


# heap budget = limit - observed native memory - safety margin
1Gi limit - 220Mi native - 190Mi margin = 614Mi heap

614Mi / 1024Mi = 60%


env:
- name: JAVA_TOOL_OPTIONS
  value: >
    -XX:MaxRAMPercentage=60

Measure native memory under load first; use a lower percentage (default is 25%) for thread-heavy services, then increase % as you understand native memory needs.

Native threads

Every OS thread brings a stack

HotSpot Linux/x64 default is commonly 1024 KB per OS thread


500 OS threads * 1MiB stack = 500MiB reserved

env:
- name: JAVA_TOOL_OPTIONS
  value: >
    -Xss512k

The JVM default is intentionally roomy. Lowering -Xss can reclaim native headroom when a process has many OS-backed threads.

Built-in tools

Native Memory Tracking gives you the map

  • Enable NMT with -XX:NativeMemoryTracking=summary.
  • It adds native-allocation bookkeeping overhead; summary is lighter than detail.
  • Use jcmd against the running JVM.
  • Use it in load tests or targeted production windows, then start with the big buckets.

🪣 Read the buckets

Read one NMT bucket


- Thread (reserved=59260KB, committed=5588KB)
          (threads #29)
          (stack: reserved=59160KB, committed=5488KB)
          (malloc=68KB tag=Thread #175)
  • 29 JVM and application threads exist.
  • Stacks reserve about 58MB of address space.
  • About 5.5MB is backed by real memory and can count toward pressure.
  • Thread count and -Xss change this budget.

🪣 Read the buckets

What usually moves the number?

  • Class: many loaded classes, frameworks, proxies, or hot redeploy behavior.
  • Thread: large servlet pools, scheduler pools, Kafka consumers, or blocking I/O.
  • Code: lots of hot methods compiled by the JIT over time.
  • GC: bigger heaps, more regions, remembered sets, and collector worker data.

Workflow

Get a picture in minutes


jcmd <pid> VM.native_memory summary
jcmd <pid> VM.native_memory baseline
# run representative load
jcmd <pid> VM.native_memory summary.diff

The goal is not perfect accounting. The goal is to stop guessing.

🚀Java Flight Recorder

Record heap behavior during tests


env:
- name: JAVA_TOOL_OPTIONS
  value: >
    -XX:+FlightRecorder
    -XX:StartFlightRecording=filename=/tmp/load-test.jfr,dumponexit=true

kubectl exec <pod> -- jcmd <pid> JFR.dump filename=/tmp/load-test.jfr
kubectl cp <pod>:/tmp/load-test.jfr ./load-test.jfr

Open the recording in JDK Mission Control to review heap usage, allocation pressure, and GC behavior across the test window.

> jcmd 1 VM.native_memory summary
Total: reserved=1726277KB, committed=80765KB

For Java heap, NMT's reserved and committed match GC.heap_info; heap_info adds used, the live heap occupancy inside that committed space.

Right-size loop

↻Measure, set, validate

  1. Confirm the JVM detects the pod's cgroup limits.
  2. Measure heap and native memory under realistic load.
  3. Utilize MaxRAMPercentage with explicit native headroom.
  4. Validate native memory usage before production traffic does finds the limits for you.
